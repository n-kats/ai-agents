# Opik 利用ノウハウ

Opik を用いて LLM 実行ログを収集する際に得た知見を整理する。ここでは一般的に転用できるプラクティスのみを記録し、特定プロジェクト固有の実装詳細には立ち入らない。

## 採用した手法
- **OpenAI クライアントのラップ**  
  `opik.integrations.openai.track_openai` で OpenAI SDK クライアントをラップすると、`chat.completions` や `responses` など代表的な API 呼び出しが自動でトレース化される。明示的なトレース開始や終了処理が不要で、トークン使用量も自動計測されるため、実装コストを抑えられる。

- **Opik インスタンスの明示注入**  
  環境変数で渡された接続先情報から `Opik(project_name=..., workspace=..., host=...)` を生成し、そのインスタンスから `project_name` を取得して `track_openai(client, project_name=...)` を呼び出す。セッション設定を介さずにトレース送信先を切り替えられ、プロセス全体の副作用も限定できる。

- **設定値が無い場合はトラッキングを無効化**  
  接続先 URL など必要な情報が未指定のときは追跡を完全にスキップし、OpenAI 呼び出しのみを継続する方針にした。Opik 連携が任意機能の場合でも基本機能を阻害せず、安全にデフォルト動作へフォールバックできる。

## 採用を見送った手法
- **セッション設定 (`update_session_config`) による差し替え**  
  セッションキャッシュを書き換える方法はプロセス内での状態共有を伴い、並列実行時の衝突リスクがある。明示的に `Opik` インスタンスを構築する方が影響範囲を局所化できるため採用しなかった。

- **手動で `Opik().trace()` を呼ぶ実装**  
  API 呼び出しごとにトレースやスパンを手作業で生成する方法は、出力整形やトークン使用量計算を自前で行う必要があり冗長だった。公式の OpenAI 連携ラッパーを使えば同等の情報をより安定的に取得できるため、手動トレースは採用しなかった。

- **環境変数の直接上書き**  
  `OPIK_*` 系の環境変数をコード側で変更する方法は、プロセス全体に副作用を及ぼしやすく運用時の衝突リスクが高い。セッション設定 API を利用すれば同等の効果を得ながら副作用を局所化できるため、環境変数の強制上書きは避けた。

## 運用上の注意
- Opik サーバーの URL は `http://localhost:<port>/api/` のように終端 `/api/` を含める。  
  実装側で `NKAA_OPIK_URL` を指定すると `OPIK_URL` / `OPIK_URL_OVERRIDE` など関連変数へ自動反映されるが、明示的に別値を入れないよう注意する。
- OSS 版の Opik はワークスペース指定を受け付けないため、`NKAA_OPIK_WORKSPACE` などを設定せず `project_name` のみで運用する。
- Opik サーバーが起動していない／到達できない場合は HTTP 接続エラーになるため、事前に接続先の疎通を確認する。
- `NKAA_OPIK_URL` を未設定にすれば追跡が無効化され、OpenAI 呼び出しだけが行われる。構成ミス時の切り戻し手段として有効。
- SDK のバージョン差異で `track_openai` が `project_name` 引数を受け取らない場合があるため、呼び出し時は例外をキャッチしてフォールバックできる設計にしておくと安定する。
