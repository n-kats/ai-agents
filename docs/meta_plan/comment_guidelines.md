# コードコメントガイドライン

このドキュメントは、本プロジェクトにおけるコード内コメントの書き方に関する基本方針を示します。目的は、コードの可読性と保守性を高め、開発者間の円滑なコミュニケーションを促進することです。

## 基本方針

- **コメントの目的**:
  - **なぜその実装を選択したのか (Why not)**: コードを読めば「何をしているか(What)」や「なぜそれが必要か(Why)」は理解できることが多い。コメントでは、**なぜ他の方法ではなく、この特定の実装を選択したのか**、検討した**代替案**とその**トレードオフ**、そして最終的な**決定理由**を記録することが重要である。これにより、将来の変更時に同じ検討を繰り返すことを避け、設計意図を明確に伝えられる。
    ```python
    # 例: 当初はXアルゴリズムを検討したが、特定のデータパターンで性能が劣化するため、
    # 計算量は増えるが安定性の高いYアルゴリズムを採用した。(Issue #456 参照)
    ```
  - **複雑なロジックの解説**: アルゴリズム、正規表現、ビジネスルールなど、コードだけでは理解が難しい部分を補足説明する。
  - **前提条件や制約**: コードが特定の前提条件（例: 入力データの形式、外部システムの挙動）に依存している場合や、意図的な制約がある場合にそれを明記する。
  - **参照情報**: 関連する設計書、Issue、外部ドキュメントへのリンクを示す。

- **コメントすべきでないこと**:
  - コードを読めば **自明** なこと。変数名や関数名が適切であれば、コメントは不要な場合が多い。
    ```python
    # Bad: iをインクリメント
    i = i + 1
    ```
  - 悪いコード（変数名が不明瞭、関数が長すぎる、ロジックが複雑すぎるなど）を **ごまかす** ためのコメント。コメントを追加する前に、まずコード自体のリファクタリングを検討する。
  - バージョン管理システム（Gitなど）で追跡できる **履歴情報**（作成者、変更日時、変更履歴など）。
  - コメントアウトされた古いコード。不要なコードは削除し、必要であればバージョン管理システムから復元する。

- **コメントのスタイル**:
  - `.clinerules` に従い、開発者向けのコメントは **である調** で記述する。
  - 一貫性のあるスタイルを保つ（例: インデント、句読点、空行の使い方）。
  - Docstring（関数やクラスの説明）とインラインコメントを適切に使い分ける。

- **Docstring**:
  - モジュール、クラス、関数、メソッドの先頭には、その目的、引数、戻り値などを説明するDocstringを記述する。
  - Pythonの場合は [PEP 257](https://peps.python.org/pep-0257/) や [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html#3.8-comments-and-docstrings) などを参考に、一貫したフォーマットを使用する。

- **TODO/FIXME**:
  - 将来的なタスクや修正が必要な箇所には `TODO:` や `FIXME:` を使用する。
  - コメントには、**具体的な内容**、**担当者**（任意）、関連する **Issue番号**（推奨）を追記する。
  ```python
  # TODO(user_name, Issue #123): 現在の実装は非効率なため、アルゴリズムを見直す必要がある。
  # FIXME: 特定の条件下で例外が発生する可能性があるため、エラーハンドリングを追加する。
  ```

- **コメントの更新**:
  - コードを変更した際は、関連するコメントも **必ず更新** する。古いコメントや不正確なコメントは、コードの理解を妨げる。
  - 不要になったコメントは **削除** する。

このガイドラインに従ってコメントを記述し、コードベース全体の品質を維持・向上させることに協力してください。
