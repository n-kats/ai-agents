# nkaa Concept Draft

- **狙い**  
  LLM ベースの複数エージェントを同時に走らせ、共通の基盤で管理できる軽量フレームワークを目指しています。プロセス制御や状態保存など面倒な部分はフレームワーク側が受け持ち、利用者は目的に合わせたエージェントロジックだけを実装する想定です。

- **エージェント実行モデル**  
  マネージャは pydantic で表現された設定 (`AgentConfig`) からエージェントを生成し、`ManagerExecutionBackend` を介してエージェント実行方法（プロセス / スレッド）を選択できます。デフォルトは `multiprocessing` による個別プロセス実行ですが、`ThreadingManagerExecutionBackend` を渡すことでサンドボックス環境などプロセス生成が制限された状況でも同じ API で動かせます。停止・保存処理は `StandardManager` がまとめて面倒を見てくれるため、拡張側は `run` / `stop` / `save` / `load` を実装すれば動かせる仕立てです。
  JSON Lines で状態を扱う単純なケース向けに `JsonLinesStateMixin`（`nkaa/framework/persistence.py`）を用意し、サンプルの `SingleAgent` で実装例を示しています。

- **ツール注入の考え方**  
  エージェントに渡す依存関係は `BaseTools` を継承したデータクラスとして束ねます。`StandardManagerConfig` は `build_tools()` で共有ツールを構築し、その戻り値を `StandardManager` へ渡すのが基本フローです。プリセットの `SingleAgentTools` が、LLM 呼び出し・ログ・ユーザー入力・停止シグナルをひとまとめにする使い方を示しています。
  具体ツール同士の継承は避け、共有コンポーネントは所有（composition）で再利用します。既存クラスを継承してフィールドを増やすのではなく、アダプター経由で必要な依存を束ねた `Tools` オブジェクトを渡し、エージェントは受け取ったオブジェクトから直接利用する方針に統一します。

- **通信とチャンネル**  
  「人がチャットツールで複数の部屋を読み書きする」体験をエージェントに持たせる構想です。チャネル関連の実装は `nkaa/framework/channels/` に集約され、`ChannelManager` がチャネルの生成・参加・メッセージ配送を担います。参加操作はマネージャーや別エージェントが代理で実施し、個々のエージェントは `ChannelTools` を通じて `receive` / `send` を呼び出すだけでメッセージの授受が可能です。未読キューのスナップショット取得（`snapshot_unread`）や永続化（`save()`）は引き続きツール側に用意しており、必要に応じて呼び出せます。チャネル本体は `SQLChannelRepository`（PostgreSQL / SQLite 対応）を含む `ChannelRepository` 実装を通じて履歴をデータベースに保存しつつ、各エージェントごとに優先度付きキューで未読を管理します。探索やアクセス制御などの高度な機能は今後の拡張ポイントとして切り出しています。

- **最近の実装メモ**  
  - アプリケーション層は `ChannelManager` を直接操作せず、`ChannelTools` を介して参加・送信・受信を行うことが基本方針。内部実装の差し替えや監査フックを集中管理するためのルールです。  
  - `ChannelTools.read` はブロッキング I/O を前提に最小 API へ整理済み。人間／LLM の応答を待つ場合は `block=True` を指定し、ポーリング等の特殊用途は将来の拡張で検討する。  
  - 参加済みチャネルの `ChannelMetadata` をまとめて取得できる `joined_channel_metadata()` を追加。プロンプト構築や UI 表示をこの情報から直接導く想定で、個別のラッパークラスは持たない方針とした。  
  - LLM から返る出力チャネル名は、受信側でメタデータ一覧と突き合わせて解決し、不明な名前は警告付きで受信元チャネルへフォールバックするのが現在の安全策。将来的にはプロンプトと連動した共通ヘルパーを追加する余地がある。

- **人間インタラクションを担うエージェント**  
  オペレーターやユーザーの入力も「対話専用エージェント」として扱います。`HumanInteractionAgent`（仮称）が CLI / GUI / ファイルなど適切な I/O ツールを持ち、他のエージェントとチャンネル越しに会話・承認・指示を行うことで、人間とのやり取りをフレームワーク内に統一できます。管理マネージャは通常のエージェントと同様にプロセス・ライフサイクルを制御し、記録やレビュー用のログ永続化もこのレイヤーで扱います。

- **プリセットの位置づけ**  
  `nkaa/presets/managers/single_agent_model.py` などは「最小構成でどう使うか」を示すテンプレートで、LLM 呼び出しも `LLMCallTool` のダミー実装になっています。実運用ではここを本物のクライアントやドメイン固有ツールに差し替える前提です。

- **想定ユースケース**  
  設定ファイルからエージェント群を立ち上げ、外部 API や自作ツールを束ねた `Tools` を注入し、必要に応じて複数チャンネルを跨ぎながら協調させる――といったワークフローを短時間で構築できる「エージェント運用の土台」として設計されています。

- **アダプターの役割と利点**  
  `StandardManager` はツール生成とエージェント生成を分離し、アダプターを間に挟むことで渡し方をカスタマイズできる設計です。共有ツールセットからエージェント固有の構成を作ったり、アクセス制御・ラップ・ログ付与などをまとめて管理できる点が強みです。エージェント側は渡された `tools` をそのまま使えばよいため実装が簡潔になり、構成変更はマネージャ側で集中管理できます。
