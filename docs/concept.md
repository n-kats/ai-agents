# nkaa Concept Draft

- **狙い**  
  LLM ベースの複数エージェントを同時に走らせ、共通の基盤で管理できる軽量フレームワークを目指しています。プロセス制御や状態保存など面倒な部分はフレームワーク側が受け持ち、利用者は目的に合わせたエージェントロジックだけを実装する想定です。

- **エージェント実行モデル**  
  マネージャは pydantic で表現された設定 (`AgentConfig`) からエージェントを生成し、各エージェントを個別プロセスで実行します。停止・保存処理は `StandardManager` がまとめて面倒を見てくれるため、拡張側は `run` / `stop` / `save` / `load` を実装すれば動かせる仕立てです。
  JSON Lines で状態を扱う単純なケース向けに `JsonLinesStateMixin`（`nkaa/framework/persistence.py`）を用意し、サンプルの `SingleAgent` で実装例を示しています。

- **ツール注入の考え方**  
  エージェントに渡す依存関係は `BaseTools` を継承したデータクラスとして束ねます。`_load_tools` でツール群を用意し、アダプター経由で各エージェントに引き渡す設計です。プリセットの `SingleAgentTools` が、LLM 呼び出し・ログ・ユーザー入力・停止シグナルをひとまとめにする使い方を示しています。

- **通信とチャンネル**  
  「人がチャットツールで複数の部屋を読み書きする」体験をエージェントに持たせる構想です。チャネル関連の実装は `nkaa/framework/channels/` に集約され、`ChannelManager` がチャネルの生成・参加・メッセージ配送を担い、生成時にチャネルへ保存用コールバックを渡します。エージェントは `ChannelTools` を通して `join/leave/send/read` を呼び出し、必要に応じてチャネルの保存実行や未読スナップショット取得（`snapshot_unread`）・永続化（`save()`）を自分で行います。チャネル本体は `SQLChannelRepository`（PostgreSQL / SQLite 対応）を含む `ChannelRepository` 実装を通じて履歴をデータベースに保存しつつ、各エージェントごとに優先度付きキューで未読を管理します。探索やアクセス制御などの高度な機能は今後の拡張ポイントとして切り出しています。

- **人間インタラクションを担うエージェント**  
  オペレーターやユーザーの入力も「対話専用エージェント」として扱います。`HumanInteractionAgent`（仮称）が CLI / GUI / ファイルなど適切な I/O ツールを持ち、他のエージェントとチャンネル越しに会話・承認・指示を行うことで、人間とのやり取りをフレームワーク内に統一できます。管理マネージャは通常のエージェントと同様にプロセス・ライフサイクルを制御し、記録やレビュー用のログ永続化もこのレイヤーで扱います。

- **プリセットの位置づけ**  
  `nkaa/presets/managers/single_agent_model.py` などは「最小構成でどう使うか」を示すテンプレートで、LLM 呼び出しも `LLMCallTool` のダミー実装になっています。実運用ではここを本物のクライアントやドメイン固有ツールに差し替える前提です。

- **想定ユースケース**  
  設定ファイルからエージェント群を立ち上げ、外部 API や自作ツールを束ねた `Tools` を注入し、必要に応じて複数チャンネルを跨ぎながら協調させる――といったワークフローを短時間で構築できる「エージェント運用の土台」として設計されています。

- **アダプターの役割と利点**  
  `StandardManager` はツール生成とエージェント生成を分離し、アダプターを間に挟むことで渡し方をカスタマイズできる設計です。共有ツールセットからエージェント固有の構成を作ったり、アクセス制御・ラップ・ログ付与などをまとめて管理できる点が強みです。エージェント側は渡された `tools` をそのまま使えばよいため実装が簡潔になり、構成変更はマネージャ側で集中管理できます。
