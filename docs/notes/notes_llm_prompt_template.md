# LLM プロンプト設計メモ（structured response 向け）

## 目的
`samples/llm_delegation.py` で採用したプロンプト設計パターンを共有し、今後のテンプレート調整や新規サンプル追加時に再利用できるヒントをまとめる。特に、構造化レスポンスを JSON スキーマ（Pydantic モデル）で指定しつつ、自然文で読みやすい指示を行う際のコツを整理する。

## コツ

1. **入力情報は自然文セクションとして渡す**  
   - JSON のキー名を列挙するよりも、`受信チャネル情報: ...` のような見出しと箇条書きで内容を示す方が LLM にとって読みやすく、指示も簡潔になる。  
   - `_format_llm_payload()` のように「チャネル情報」「メッセージ」「利用可能チャネル」の3ブロックと決めておくと、プロンプト側で参照しやすい。

2. **出力形式は BaseModel（JSON スキーマ）に任せる**  
   - プロンプト中で `output_channel` や `message.role` の説明を繰り返さず、Pydantic モデルに定義された型・フィールド名へ委ねる。  
   - プロンプトでは「投稿先」「メッセージ種別」「本文テンプレート」など LLM の判断に必要な情報だけを書き、余計な形式説明を省く。

3. **投稿ルールは条件分岐ではなく「箇条書きルール」**  
   - 「受信チャネルが human_support のときは〜」「analysis_workspace からの analysis_summary は〜」という規則を簡潔に列挙。  
   - 条件を満たさない場合は投稿しない、と明示することで不要な出力を抑制できる。

4. **本文テンプレートを明示する**  
   - `要約: ...` や `推奨アクション:` などの見出しを固定し、LLM がそのまま記載するよう指示すると、content が安定する。  
   - 箇条書きの数や粒度も「短い具体文で」といった形で制約を入れると、ばらつきが減る。

5. **メタデータの扱いは「必要なら転記」で済ませる**  
   - request_id や metadata をいつ引き継ぐかは短く書くだけで十分。  
   - LLM に判断を任せる部分は「必要に応じて転記」と曖昧にせず、記載元のセクション名を参照させるとよい。

6. **余計な文章を禁止し、投稿回数を固定する**  
   - 「出力は 1 回の投稿のみ」「余計な文章は付けない」と明示することで、構造化レスポンス以外のテキストを防げる。

## 参考
- 実装例: `samples/llm_delegation.py` の `FRONT_DESK_SYSTEM_PROMPT` / `THINKING_SYSTEM_PROMPT`
- 入力メッセージ整形: `_format_llm_payload`
- 構造化レスポンス: `StructuredChannelResponse`（Pydantic モデル）
